Pratik fark:
- update_job → tasker plugin gibi job'un output.values'ına satır ekleyenler kullanır (tasker/plugin.py:88 aslında update_plugin ediyor, ama theoretical use case bu)
- update_plugin → her plugin'in kendi datasını döndürmesi (TMDb show metadata'sı, scanner targets listesi vb.)

Senin sorunun: "update_plugin gerek mi, create_job + update_job yetmez mi?"
Cevabım: update_plugin hem mantıksal olarak ayrı bir concern (job state ≠ plugin output) hem de routing yapıyor (target_id prefix → run.plugins veya job.plugins). update_job ile aynı işi yapabilirdik ama o zaman plugin yazarı update_job(key="plugins.tmdb.show", ...) gibi long path yazmak zorunda kalırdı + run-scope yazmak için ayrı API yine gerekirdi. B1. Plugin output standardı (gönüllü convention, zorlama yok)

- Ana objeler kategori olur. TMDB için: show ve movie (sadece bu ikisi).
- episode, season, validation, media_type ANA KATEGORİ DEĞİL — bunlar show'un alt field'ları:
show:
  title: {primary, original, localized}
  season_number: 1            # düz field, json değil
  episode_number: 1           # düz field, json değil
  episode_title: "Pilot"      # düz field
  overview: "..."
  # diğer metadata
- TMDB bir çağrıda ya movie döner ya show. İkisini birden değil.
- Diğer metadata pluginleri (omdb, tvmaze, tvdb) TMDB'nin formatına gönüllü uyar.
- Anime gibi yeni kategoriler ileride eklenebilir.

B2. Input plugin'leri için convention

- file-reader, scanner gibi pluginler ortak files (veya input) kategorisi altında dönsün.
- Renamer files shape'ine uyum sağlasın — sadece parsed field'ını ekleyerek.
- Standart sayesinde files namespace'inde aynı shape olur, plugin'ler birbirinin verisini görebilir.

B3. Kategoriler core'da hardcoded YOK

- manifest.categories field SİLİNECEK (sadece UI summary için, pipeline'da kullanılmıyor — zaten doğrulandı).
- Sistem hangi kategorilerin var olduğunu BİLMEZ. Plugin'in döndüğü dict'in kök key'leri otomatik kategori olur.
- TMDB show döndürürse, sistem onu "show" kategorisi sayar — özel bilgisiz.

B4. Birleşik data envelope (lazy/on-demand)

- runtime state'te run, jobs, plugins (flat) dışında yeni bir data alanı olur (veya plugins flat silinir, data onun yerine geçer).
- data envelope = tüm plugin verilerinin birleştirilmiş, priority resolved view'ı.
- Pull-based, on-demand: her okuma anında merge yapılır, ekstra storage yok.
- Job ve run ayrımı KORUNUR. data.<jobindex>.<kategori>... veya data.<runindex>.<kategori>... şeklinde access edilir.

B5. Config'de data_priority paradigması (HARDCODED YOK, full path)

Senin son netleştirmen:

data_priority:
  # Job-scope priority (current_job_id alias ile)
  "data.${current_job_id}.movie":              [tmdb, omdb]
  "data.${current_job_id}.show":               [tvmaze, tmdb]
  "data.${current_job_id}.show.episode_title": [tmdb]            # daha spesifik field override

  # Run-scope priority
  "data.${current_run_id}.input":              [scanner, file-reader]

VEYA daha temiz (alias kısaltmalı):
data_priority:
  "data.<jobindex>.movie":              [tmdb, omdb]
  "data.<jobindex>.show.episode_title": [tmdb]
  "data.<runindex>.input":              [scanner, file-reader]

B6. Priority kuralları (longest-prefix wins)

1. Daha spesifik path baskın. data.<job>.show.episode_title: [tmdb] baskın — data.<job>.show: [tvmaze] daha genel.
2. Belirtilmemiş alt field için → büyük scope priority devralır (yani data.<job>.show'a tvmaze atandıysa, episode_title belirtilmemişse tvmaze'in episode_title'ı kullanılır).
3. Hiç plugin atanmamışsa → ilk veri giren plugin baskın (insertion order).

B7. Run vs Job ayrımı KORUNUR (final karar)

- Brainstorm yaptın, run kaldırma reddedildi.

- Her job içinde renamer/tmdb/etc. çalışır. Standart input formatı job seviyesinde.

B8. RAW data — gelecek

- Şimdi RAW gerek yok. Metadata pluginleri ileride RAW eklerse ayrı namespace'te saklanır (raw veya benzeri).

class ConfigRenderEngine:
    def __init__(self, jinja_env=None):
        self.env = jinja_env or Environment(loader=BaseLoader())
        # filter'lar: count, format, tojson, vs.

    def render_value(self, value, context):
        """String ise Jinja render et, dict/list ise recursive descend."""
        if isinstance(value, str) and ('{{' in value or '{%' in value):
            tmpl = self.env.from_string(value)
            return tmpl.render(**context)
        if isinstance(value, dict):
            return {k: self.render_value(v, context) for k, v in value.items()}
        if isinstance(value, list):
            return [self.render_value(item, context) for item in value]
        return value  # int, bool, None — pass-through
